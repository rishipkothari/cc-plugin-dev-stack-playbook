# Log a project in the central history

The central history is `projects.md` in the GitHub repo `rishipkothari/dev-stack-playbook`, branch `main`. It is shared across all devices, so always read and write the **GitHub copy**, never the copy inside the installed plugin (that is a read-only cache and may be stale).

## projects.md format

```markdown
# Projects

<!-- coverage:start -->
## Coverage
…generated, never edited by hand…
<!-- coverage:end -->

## Projects

### <project-name>
- **Summary:** <one sentence>
- **Repo:** <owner/repo> · **Stack doc:** <link to docs/stack.md>
- **Started:** <YYYY-MM> · **Status:** planned | in progress | live | archived
- **Learning goals:** <short>
- **Stack:**
  - Hosting: <option>
  - Framework: <option> ★
  - …
- **Notes:** <optional: lessons, what you'd change>
```

Projects are listed newest first. ★ marks an option that was new to the user in that project. List only components that apply; omit "Not needed" ones.

## Steps

### 1. Gather the project's details

- Prefer the project's `docs/stack.md` (written by `plan-stack`). Otherwise read the codebase (package.json, config files, env var names) and ask the user to confirm what you inferred.
- Confirm the status and anything the user wants in Notes.

### 2. Get the current history

Get `projects.md` from the GitHub repo, using the first method that works:

1. A local clone of `rishipkothari/dev-stack-playbook` (check the working directories and common locations like `~/dev-stack-playbook`, `~/code/dev-stack-playbook`, `~/projects/dev-stack-playbook`; ask the user where it is if not found). `git pull` first.
2. In a Claude Code cloud session: attach the repo to the session (add-repo tool), clone it, and use it as a local clone.
3. The GitHub connector or MCP tools (read the file contents and its SHA).
4. The `gh` CLI (`gh api repos/rishipkothari/dev-stack-playbook/contents/projects.md`).

If none works, ask the user to paste the current `projects.md`, or proceed from an empty file and tell them.

### 3. Update the entry

- If the project already has an entry (match by name or repo), update it in place. Otherwise add it at the top of the Projects section.
- Determine ★ markers: an option is new if no older project in the file uses it. Keep markers the user set explicitly.

### 4. Regenerate the coverage section

Rebuild everything between `<!-- coverage:start -->` and `<!-- coverage:end -->` from the project entries:

```markdown
## Coverage

_Generated by the log-project skill from the entries below. Last updated <YYYY-MM-DD>; <N> projects._

| Component | Used (projects) | Not tried yet |
| :- | :- | :- |
| Hosting | Vercel (2), Render (1) | Netlify, Cloudflare, Railway, Fly.io, VPS + Coolify, GitHub Pages |
| … | | |
```

- One row per component in the playbook's component map (README.md → "Component map"), in that order.
- "Used" counts projects per option.
- "Not tried yet" lists the options from the component map row (★, ◆ and ✦ columns) that no project has used.
- Read the component map from the playbook's `README.md` (`${CLAUDE_PLUGIN_ROOT}/README.md`, or the same repo).

### 5. Show and confirm

Show the user the new or changed entry and a summary of coverage changes (e.g. "first time using Turso"). Ask before writing to GitHub.

### 6. Write it back

Using the same method as step 2:
- Local clone: edit, `git add projects.md`, commit with a message like `Log <project-name>: <status>`, and push to `main`.
- GitHub connector/MCP: update the file with its current SHA (re-read and merge if the SHA changed).
- `gh` CLI: `PUT` the contents API with the SHA.
- No write access (e.g. a chat without GitHub write tools): give the user the full updated `projects.md`, or the exact entry to paste under `## Projects` and the new coverage section, and tell them where.

Then confirm what was written and where.
